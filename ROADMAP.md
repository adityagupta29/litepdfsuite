# PDFPress Roadmap

Living project doc. Read this first in any new session before touching the codebase — it has the "why" behind decisions that aren't visible in the code.

## What this site is

Static, 100% client-side PDF tool suite. No backend, no upload — every tool runs entirely in the browser via `pdf-lib` (write/edit), `pdfjs-dist` (render/read), and format-specific libs (`jszip`, `docx`, `xlsx`, `pptxgenjs`) loaded from jsdelivr CDN. "Files never leave your browser" is the core brand promise — every new tool must honor it. No server-side processing, ever.

Brand system: Fraunces (display serif) + Space Grotesk (body sans), Font Awesome 6.5.1, light/dark theme via `data-theme` + CSS custom properties. Each tool gets its own accent gradient (`.tool-icon.t1`..`t5`...) matching its homepage card icon. Reuse shared component classes (`.btn`, `.toast`, `.processing`, `.upload-zone`, `.modal-overlay`) rather than reinventing per tool.

## Research: what professional/office/student users in India actually need

Sources: iLovePDF/Smallpdf feature comparisons (2026), and India-specific search on what govt-employee/student PDF workflows look like.

Key findings:
- **iLovePDF-style baseline** that any serious PDF suite is expected to cover: merge, split, compress, rotate, convert (Word/Excel/PPT/JPG both ways — we already have this), OCR, e-signature, watermark, unlock/protect.
- **India-specific pattern that's distinct from generic "PDF tools" lists**: government/exam form portals (SSC, UPSC, RRB, banking exams, state PSCs) impose strict file-size caps on uploads — e.g. "photo must be under 20–50KB", "signature under 20KB", "certificate PDF under 200KB/1MB". This drives huge organic demand for **"compress PDF/image to exact target size"** and **"resize photo/signature to exam spec (dimensions + KB)"** tools specifically, more than in most other markets. Worth treating as a first-class distinct tool, not folded generically into "compress."
- Students combine multiple scanned certificates/marksheets into a single PDF for uploads → covered by our existing Merge tool, but a dedicated **Split PDF** (reverse direction: pull specific pages back out, e.g. extracting one marksheet page from a combined scan) is a commonly paired need.
- Office workers handling service books, pension paperwork, RTI/internal files want **password protect / remove password**, **watermark (draft/confidential)**, and **e-signature**.
- Sensitive documents (Aadhaar, PAN, bank statements) make "processed 100% locally, never uploaded" a genuine trust/marketing point specific to this audience — lean into it in copy for every new tool.

## Build order (agreed sequencing — revisit if priorities shift)

Batch by shared infrastructure to avoid rebuilding the same page-thumbnail/upload-zone UI four times:

1. **Split PDF** ✅ shipped 2026-08-14 — reused merge-tool's page grid, added Extract Selected / Custom Ranges / Every N Pages / Each Page Separate modes with JSZip multi-file download
2. **Rotate PDF** ✅ shipped 2026-08-14 — page grid with per-page hover quick-rotate buttons plus bulk select+rotate (left/right/180°/reset), live rotated-thumbnail preview, verified rotation angles land correctly in the exported PDF
3. **Compress PDF** + **Compress to Target Size** ✅ shipped 2026-08-14 (single tool, `compress-pdf.html`, two modes) — rasterizes each page to canvas once, then re-encodes as JPEG at a chosen quality; Quality-Level mode uses 3 presets (Small/Balanced/High) or a custom quality slider, Target-File-Size mode picks a render resolution from the target/original ratio then binary-searches JPEG quality (7 iterations) against cached canvases (no re-render per try, so the search itself is fast even though each full-document build is not free). Verified against a real generated PDF: 681KB → 144.6KB hit a 150KB target in ~2s. Clearly labeled in the UI that output is image-based (no selectable text) since true PDF stream recompression isn't practical client-side.
4. **Image/Signature Resizer for Exam Forms** ✅ shipped 2026-08-14 (`photo-resizer.html`) — not a PDF tool, a standalone photo/signature cropper: drag-to-pan + zoom-slider cover-fit cropper over a fixed-aspect frame, preset dropdown (SSC/UPSC/IBPS/PAN/passport, each with an explicit "specs change often, verify official notification" caveat) or custom W×H, JPEG binary-search-to-target-KB (same pattern as Compress PDF) or lossless PNG. Verified: 3 sequential exports with different dims/formats in one session (200×230 JPG, 200×80 JPG, 300×300 PNG) all downloaded correctly with distinct filenames; PNG output dimensions confirmed pixel-exact by reading the IHDR chunk directly.
5. **Watermark PDF** ✅ shipped 2026-08-14 (`watermark-pdf.html`) — text or image mode, tiled or 9-point-anchor positioned, opacity/rotation/size sliders, page-range restriction (reuses Split PDF's range-parsing pattern), live canvas preview of page 1 mirroring the final pdf-lib output. **Real bug found and fixed during verification**: the position-anchor math was shared between the canvas preview (y=0 at top) and the actual pdf-lib export (y=0 at bottom) without accounting for the flipped Y axis — "bottom-right" was landing at top-right in the real output while looking correct in the preview. Caught by actually rendering the exported PDF back through pdfjs and screenshotting it, not by reading the preview alone. Fixed by adding a `pdfSpace` flag to the shared anchor function. Lesson: **a live preview that reads the same state as the export can still diverge from the export if the two rendering targets use different coordinate conventions — always verify the literal exported file, never trust the preview as a proxy for it.**
6. **Extract Images from PDF** + **PDF to Text** ✅ shipped 2026-08-14, combined into one tool (`extract-pdf.html`, two mode tabs) since both are pdfjs read-only extraction sharing the same upload/preview shell. Text mode: per-page `getTextContent()` with a y-position line-break heuristic, optional `--- Page N ---` markers, live scrollable preview built once on load. Images mode: **not** page rasterization (that already exists as "PDF to Images" in the Converter tool) — this walks each page's operator list, tracks the CTM through `save`/`restore`/`transform` ops to find the real placement rectangle of every `paintImageXObject`/`paintJpegXObject` call, then crops those regions out of a high-res page render (2x scale) and re-encodes as PNG. A "skip small icons/decorations" toggle filters by area-ratio + min-dimension. Verified against a purpose-built test PDF with 2 real embedded images (300×200 "photo" placed at 300×200pt, 120×120 graphic) plus one 20×20pt icon: found exactly 2 with the filter on, exactly 3 with it off, and the extracted PNGs were pixel-verified as clean crops of the originals (no bleed from surrounding page content).
7. **e-Sign PDF** ✅ shipped 2026-08-14 (`esign-pdf.html`) — signature source is a transparent PNG regardless of how it was created (drawn on a canvas pad and auto-trimmed to its content bounding box; typed and rendered through one of 4 cursive Google Fonts onto an offscreen canvas; or uploaded directly), which sidesteps embedding fonts into the PDF entirely — the signature is always just an image by the time pdf-lib touches it. Placement is a draggable/resizable overlay div on a live single-page preview, with prev/next page navigation. Applied the canvas-vs-PDF Y-axis lesson from Watermark PDF from the start (no bugs found this time): overlay position is tracked in CSS px, top-left origin, and only converted to PDF point space (bottom-left origin) at export time. Verified with both a typed signature (dragged to top-left, confirmed landing exactly there in the re-rendered output) and a drawn signature (resized via the corner handle, confirmed correct scale in the output) — two distinct signature methods on two different pages in one session, no filename collisions.
8. **Crop PDF** ✅ shipped 2026-08-14 (`crop-pdf.html`) — crop region is stored as four edge fractions (left/top/right/bottom, in the intuitive "margin trimmed from this edge" sense) rather than absolute points, so the same crop can be reapplied consistently across pages of different sizes. A real bug was caught here **before shipping, via reading the pdf-lib source directly rather than by testing**: `page.setMediaBox()` alone isn't sufficient — many PDFs carry an explicit CropBox that viewers prioritize over MediaBox for display, so a MediaBox-only crop could silently fail to appear in some viewers while "succeeding" by every automated check available (page count, MediaBox dimensions). Fixed by calling `page.setCropBox()` with the same rectangle immediately after `setMediaBox()`. Lesson: **when a library exposes multiple related properties for the same visual concept (here, MediaBox vs. CropBox vs. TrimBox), grep the library's own source for sibling getters/setters before assuming the one you found is the only one that matters** — this class of bug is invisible to output-file verification because the "wrong" file is still perfectly valid, just under-specified.
9. **Compare PDFs** ✅ shipped 2026-08-14 (`compare-pdf.html`) — reused the extraction heuristic from Extract Text & Images, diffs the two line arrays with a standard LCS dynamic-programming table (O(n·m), guarded at 3000 lines/side to keep memory bounded), renders as a unified colored diff (red=removed from A, green=added in B) with long unchanged runs collapsed to a "⋯ N unchanged lines ⋯" marker. "Ignore whitespace" and "collapse unchanged" toggles re-render instantly. Verified against a purpose-built two-version contract PDF with known edits: exact diff stats matched hand-calculation (+3/-2/=4 lines) and every expected added/removed/unchanged line was found in the right place.
10. **Grayscale PDF** ✅ shipped 2026-08-14 (`grayscale-pdf.html`) — same rasterize-and-recompress pipeline as Compress PDF, plus a manual per-pixel luminosity desaturation pass (`0.299R + 0.587G + 0.114B`) via `getImageData`/`putImageData` rather than relying on canvas `filter: grayscale()` (which has inconsistent support), applied before the JPEG re-encode. Thumbnails use a cheap CSS `filter: grayscale(100%)` for an instant live preview without re-processing. Verified at the pixel level: sampled ~5000 pixels across the exported PDF's rendered page and confirmed `max(|R−G|, |G−B|, |R−B|) === 0` for every one — true grayscale, not just visually close.
11. **OCR** ✅ shipped 2026-08-14 (`ocr-pdf.html`) — spike confirmed tesseract.js@5.1.1 works entirely from CDN (main script + its own WASM core + per-language `.traineddata.gz`, all auto-fetched from jsDelivr, no self-hosting or special server headers needed; verified every URL with a raw `curl -I` before writing any code). `Page.words[].bbox` (`{x0,y0,x1,y1}` in source-image pixel space) confirmed by installing the package locally and reading its shipped `index.d.ts` directly — the docs/README fetched via WebFetch were too thin to trust for something this fiddly to debug after a multi-minute run. Searchable-PDF mode draws each word as real, selectable pdf-lib text at `opacity: 0` (a legitimate PDF technique — the text stays in the content stream and is respected by Chrome/Firefox/Adobe's text layer, just never painted) positioned from the bbox with the by-now-standard canvas→PDF Y-flip, and width-scaled to the bbox via a manual `pushGraphicsState()`/`concatTransformationMatrix()`/`popGraphicsState()` wrap around `drawText()` since pdf-lib has no built-in horizontal-scale option. **A real bug was caught before running the (expensive, multi-minute) test**: initial code called a nonexistent `PDFLib.concatTransform()` — grepping the installed package's `operators.js` for the actual export name (`concatTransformationMatrix`) found it in seconds, versus what could have been a very slow trial-and-error debug loop given OCR's runtime cost. Plain-text mode and page-range restriction verified correct; the invisible text layer was verified twice — once by re-extracting text from the output PDF via pdfjs (confirming both position and content), once visually via screenshot (confirming zero rendering artifacts). Real OCR runtime on a small 2-page test document was ~2-3s, far faster than the 1-3+ minute estimate from research — that estimate was for realistic multi-page scanned documents with dense/noisy content, so the UI's conservative wait-time warning stays as-is.
12. **Protect/Unlock PDF** ✅ shipped 2026-08-14 (`protect-pdf.html`) — settled on `@neslinesli93/qpdf-wasm@0.3.0`, the real QPDF C++ engine compiled to WASM (1.3MB), loaded via a plain `<script src>` tag (its Emscripten UMD wrapper falls through to a bare top-level `var Module`, which becomes `window.Module` in a classic script — no bundler, no `+esm` proxy needed). **A false negative nearly killed this option**: grepping the *JS glue file* for "encrypt" found nothing, which looked like this build had no encryption support at all — the real QPDF CLI strings (`--encrypt`, `--decrypt`, `--password=`, `R6`, AES-128/256 references) turned out to live in the *`.wasm` binary itself*, not the glue code, and only showed up once I grepped that file directly. Confirmed for real with a live headless-Chrome round-trip before writing any UI: encrypted a test PDF with `--encrypt`, confirmed `--check` correctly rejects it with no password (`invalid password`), decrypted with the right password via `--password=X --decrypt`, and verified the decrypted bytes reload cleanly in pdf-lib — genuine AES-256 protection, not a cosmetic flag. UI has two modes (Add Password / Remove Password, the latter requiring the user already know the password — not a cracking tool), an AES-256/AES-128 strength toggle, and parses qpdf's own stderr (via the `printErr` callback) to turn "invalid password" into a friendly error instead of a generic failure. Verified end-to-end through the real UI: protect → confirmed pdf-lib refuses to open the output without a password → wrong-password unlock attempt fails gracefully with no file downloaded → correct-password unlock produces a valid, fully-open PDF.
13. Redact / Repair / PDF-A — revisit later, currently deprioritized

## Conventions to follow for every new tool

- New file: `<verb>-pdf.html` naming pattern (matches `add-page-number-pdf.html`, `merge-rearrange-pdf.html`) or `pdf-<noun>.html` (matches `pdf-editor.html`, `pdf-converter.html`) — pick whichever reads more naturally for the tool name.
- Add homepage card in `index.html`'s `#tools` grid: new `.tool-icon.tN` gradient class in the `<style>` block, real Font Awesome 6.5.1 icon (verify it exists against the actual CSS before using — we shipped a bug once with a non-existent icon class), `reveal dN` stagger delay.
- `beforeunload` native warning only for tools with meaningful in-progress editing state (editor-style tools). Simple one-shot converters don't need it. **Do not add sessionStorage-based auto-save/recovery** — this was tried on the PDF Editor and explicitly reverted per user request; native browser warning only.
- Every tool must state its client-side-only privacy guarantee somewhere in its UI copy — this is a real trust signal for this audience (Aadhaar/PAN/exam docs).
- Verify with real headless-Chrome (Puppeteer) testing, not just code review: upload real files, drive the actual UI, inspect the actual output file content (unzip docx/xlsx/pptx, render PDF pages to screenshot). This caught real bugs before (font glyph-subsetting drop, pptxgenjs global collision, focus/blur race) that code review alone missed.
- **Toast container must never sit at `bottom-right`** — every tool's primary action button (`.generate-btn` / submit button) also tends to live at the bottom of a right-hand sidebar, and a `position: fixed; bottom; right;` toast will physically overlap and intercept clicks on it. Found on Split PDF: a lingering "Loaded PDF" toast silently ate a click on "Split & Download". Fixed by moving toast-container to `top: 78px; right: 24px` (below the topbar) with `flex-direction: column-reverse` and `pointer-events: none` on the container itself (`pointer-events: auto` on individual `.toast` elements) as a defensive backstop. Apply this same positioning to any tool still using bottom-right toasts.
- **PDF coordinate space has Y=0 at the BOTTOM of the page; canvas/DOM coordinate space has Y=0 at the TOP.** Any tool with both a live canvas preview and a pdf-lib export (Watermark PDF, and future ones like Crop/e-Sign) needs separate Y-axis math for the two — don't share one position-calculation function between them without an explicit flip, and don't trust the preview looking right as proof the export is right. Verify by rendering the actual exported PDF back through pdfjs and screenshotting it.
- **Never reuse one static filename for multiple distinct outputs of the same button.** This bug shipped TWICE in a row (Split PDF, then Compress PDF, same session) before it became habit — it's easy to miss because it only surfaces on the *second* differently-configured export in one browser session, which a single manual click-through won't catch. Symptom: the download silently vanishes (no error, no toast, headless-Chrome's filename-collision handling doesn't reliably surface a `(1)` suffix in all contexts — plausibly true in real browsers too for some users). Fix: always build the output filename from what was actually produced, e.g. `${baseName} - split (every 4 pages).zip`, `${baseName} - compressed (target 150KB).pdf`. **When testing any new tool, always trigger two different export configurations back-to-back in the same page session** (not just one) — that's the only way this class of bug shows up.
- **When checking whether a compiled WASM library supports some feature, grep the `.wasm` binary itself, not just its JS glue/wrapper file.** Found on Protect/Unlock PDF: grepping qpdf-wasm's `.js` glue for "encrypt" found nothing, which looked like a dead end for the whole tool — the real CLI strings (`--encrypt`, AES references, etc.) were compiled into the `.wasm` file's data section and only appeared once that file was searched directly (`grep -ao` works fine on a wasm binary despite it being "binary" — string literals inside it are still plain ASCII bytes). A negative result from the wrong file nearly caused a wrong build/no-build call.
